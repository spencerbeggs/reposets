# JSON schemas are declared in a config, not generated by a script

## Context

A previous hand-rolled generator script composed `@effected/schemastore`'s
`StoreDocument`, `SchemaValidator` and `SchemaFile` primitives itself and
ran under `tsx`. `@effected/schemastore` 0.12 moved the ajv validation
engine out of the library and into `@effected/schemastore-cli`
(`AjvValidator.layer`), so the library stopped exporting
`SchemaValidator.layer` and the script's own composition broke.

## Decision

`package/lib/configs/schemastore.config.ts` is a `defineConfig({...})`
export naming `ConfigSchema` and `CredentialsSchema`, built by the
`schemastore` bin from `@effected/schemastore-cli` — `pnpm schema:build`
runs `schemastore build lib/configs/schemastore.config.ts` and `pnpm
schema:check` runs the same config under `check`[^package-json]. The
config declares documents; the CLI owns build, validate and write.

Several values in the config are load-bearing:

- **`outputDir: "../../schemas"`** resolves relative to the config file's
  own directory (`package/lib/configs/`), landing output at
  `package/schemas/`[^schemastore-config].
- **Entry keys are the published file base names** — `reposets.config.schema`
  and `reposets.credentials.schema` — each `layout: "flat"` with no
  `versions` set, under a `baseUrl` pointing at the raw GitHub URL for
  `package/schemas/` on `main`[^schemastore-config]. `defineConfig` has no
  `$id` override field, so the entry key, the layout and the base URL are
  the only levers available, and together they derive a `$id` byte-identical
  to the URLs the SchemaStore catalog already pins for these two documents.
- **`published: true` on both, with top-level `drift: "allow"`.** Both
  schemas are genuinely listed in the SchemaStore catalog, but unversioned
  — the catalog entry points at `main`, the moving edge — so there is no
  version label a `drift: "error"`/`"semantic"` gate could bump into.
  `drift: "allow"` preserves the old generator's regenerate-in-place
  behavior while `published: true` still records that outside consumers
  depend on these files. Revisit this pairing if the schemas ever adopt
  `versions`.
- **`catalog: { description, fileMatch }`** on each entry produces the
  committed `package/schemas/catalog.json`, whose `name` and `url` fields
  derive from the entry key[^schemastore-config].
- **No `jsonSchema: { onExcessProperty: "error" }` pin.** 0.12 closes
  generated objects by default. Both TOML files decode strictly against
  their Effect Schemas, so the published JSON Schema must reject unknown
  keys too — and now does, without needing the pin.

`schema:build` is cached on `src/schemas/**` and the config file, and both
`build:dev` and `build:prod` depend on it, so a package build always runs
against freshly generated schemas rather than a stale copy[^turbo-json].

`@effected/schemastore` and `@effected/schemastore-cli` are pinned as a
fixed pair (`catalog:effected`) because the CLI's peer range on the
library is exact[^package-json]; the two are bumped together. Strict ajv
validation and the annotation-placement checks (the `x-taplo` and
`x-tombi-*` keyword families surviving the Draft-07 lowering) are the
CLI's job now, not this repository's — a misplaced annotation fails
`schema:build`/`schema:check` rather than silently degrading an editor.

## Alternatives rejected

- **Keep a hand-rolled script.** Composing `StoreDocument`, a validator
  and `SchemaFile` directly means re-implementing whatever the CLI moves
  or renames on every `@effected/schemastore` bump, with no compile-time
  signal beyond a runtime `Layer.mergeAll` failure when a re-exported
  symbol quietly disappears.
- **Pin `onExcessProperty: "error"` explicitly.** Redundant against 0.12's
  default of closing generated objects, and a pin that stops matching the
  library's own default is a second place the strictness decision could
  drift out of sync.

## Consequences

- `schema:build` and `schema:check` both run against the same config
  file, so there is exactly one place that can describe the published
  documents differently from what CI gates on.
- `tsx` is no longer a package dependency; nothing else in this package
  needed it.
- A schema entry left out of the config fails nothing at build time — the
  only symptom is an editor that silently stops completing the
  corresponding TOML file.
